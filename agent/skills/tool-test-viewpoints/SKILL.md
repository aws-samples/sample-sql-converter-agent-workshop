# テストの観点

実行テストは、次の4つの観点でケースを作る。観点ごとに最低1件を目安にする。対象に当てはまらない観点は、作らずに
「対象外」とその理由を書く（例: 引数がないので境界値は対象外）。同じ入力で、Oracleの元のSQLとPostgreSQLの変換後のSQLを
実行して、結果を比べる。

| 観点 | 作るケース | 例 |
|---|---|---|
| 正常系 | 代表的な入力。業務でよく通る経路 | 存在する社員のIDで検索する、明細のある注文を処理する |
| 境界値 | NULL、空文字、0、最大値・最小値、結果が0件・1件・複数件 | 給与がNULLの社員、該当なしの条件、明細が空の注文 |
| 異常系 | エラーになる入力で、Oracleと同じ扱いになるか（同じ種類の例外が上がる、同じ例外ハンドラに入る、同じ件数で止まる） | 存在しないID（NO_DATA_FOUND）、一意制約の違反、型の変換エラー |
| エッジケース | Action Itemや変換で書き換えた箇所に固有の動き | DBMS_OUTPUTの出力、COMMIT / ROLLBACKの有無、ROWNUMと並べ替えの関係、動的SQLの分岐ごとの組み立て、NULLを含む文字列の連結 |

## 決まりごと

- 結果は、値まで比べる（SELECTは行と列の値、DMLは成否と影響を受けた行数、プロシージャは出力や更新後の表の内容）。
  型や書式の違い（`05:30:00`と`+00 05:30:00.000000`など）は、意味が同じかを判断し、違いを書く。
- 異常系は、エラーの文言ではなく、エラーの種類（Oracleの例外名とPostgreSQLのSQLSTATE、例: NO_DATA_FOUNDとP0002）と、
  その後の動き（例外ハンドラに入ったか、処理が止まったか）で比べる。
- 既存のデータは変えない。データが必要なケースは、既存の行と重ならないキーのテスト用の行で作り、テストの後で削除する。
- ケースを増やすために、同じ観点のケースを何件も作らない。観点ごとに、変換で書き換えた箇所を通るケースを優先する。

## 報告

- `oracle_test.sql` / `postgres_test.sql`には、ケースごとに番号と観点を付けたSQLを、`oracle_test.txt` / `postgres_test.txt`には
  その結果を、`comparison_result.txt`には、ケースごとの観点、入力、一致したか、差異の原因と影響を書く。
- OK.txt / NG.txtの「テスト結果サマリー」の「観点ごとの内訳」に、観点ごとの件数と、対象外の観点とその理由を書く。
- app trackでは、ファイルごとのOK.txt / NG.txtに同じ形で書き、結果の報告にもSQLごとの観点と件数をまとめて書く。
