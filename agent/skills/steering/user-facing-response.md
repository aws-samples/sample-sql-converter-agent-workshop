# ユーザーへの応答のルール

SCAW2.0のすべてのエージェントは、ユーザーに見せる応答を作るときにこのルールに従う。
個々のSkillの記述よりも、このルールを優先する。

## 結果を伝える

- 何を変換したか、何を確かめたか、どこに出力したか、何の確認が必要かを伝える。
- MCPツールの名前、ツールを呼び出すコード、ツールの呼び出し順は応答に書かない。
- 入力が足りなければ、何が必要かを具体的に尋ねる。

良い例:

> `SCHEMA.PROC_NAME`を変換しました。`ROWNUM`によるページングを`ROW_NUMBER() OVER (...)`に、`DECODE`を`CASE`に
> 置き換えています。OracleとPostgreSQLの両方で実行し、結果が一致することを確かめました。`./result/PROC_NAME/`に
> 出力しています。

ツールの名前を出してよいのは、ユーザーがツールについて尋ねたとき、ツールのエラーを調べているとき、
ユーザーがツールを使って何かを作ろうとしているときだけである。

## パスの扱い

- 絶対パス（`/`で始まる）は、そのままツールに渡す。先頭の`/`を取ったり、作業ディレクトリを付け足したりしない。
- `~`で始まるパスは、展開せずにそのまま渡す。
- 相対パス（`./input/...`など）は、聞き返さずに、`kiro-cli chat`を起動したディレクトリ（通常はリポジトリのルート）を
  起点に絶対パスにしてからツールに渡す。
- パスが見つからないときだけ、どの絶対パスとして探したかを示して確認する。

## 出力ファイル

変換結果のファイルは、必ず対応するMCPツールで書き出す。`fs_write`で自分でファイルを作らない。

- db track: `write_db_result`
- app track: `write_app_convert_outputs`
- 変換パターンの追記: `write_skill_draft`（参加者が追記案を了承してから呼ぶ）

ツールがエラーを返したら、内容を読んで直し、もう一度呼ぶ。書き出しが成功したことを確かめるまで、
「書き出した」「確かめた」と報告しない。実行していないテストを「実行した」と書かない。
