# アプリケーションの埋め込みSQLの変換手順（app track）

SQLの文字列リテラルの中身だけを書き換え、まわりのコード（制御構造、変数、文字列の連結、バインドの呼び出し）は
変えない。構文ごとの書き方は`domain-conversion-rules`、出力の形式は`tool-output-layout`に従う。
Pro*C（`.pc`）のファイルは`domain-proc-to-ecpg`に従う（実験的機能）。

## 手順（1ファイル・1つのSQLずつ変換する）

1. **SQLを探す**: `scan_for_sql_files`でSQLを含むファイルを探し、分類（`category`）ごとに次のツールで位置を特定する。
   ツールの結果は手がかりとして使い、置き換える範囲はファイルを読んで決める。ツールが失敗した（`ok: false`など）
   ファイルは、読んでSQLの位置を特定する。
   - `source`（Java、Pythonなど）: `detect_sql_by_opengrep`（まとめて渡す）。`dynamic: true`は、文字列の連結や
     `StringBuilder`で組み立てるSQL（`tool-opengrep-ruleset`）。
   - `xml`（MyBatisなど）: `detect_xml_sql`（`<if>`、`<choose>`などの動的タグにも対応）
   - `properties`: `detect_properties_sql`、`sql`: `detect_sql_file`、`proc`: `detect_proc_sql`
   1000ファイルを超える場合は、そのまま進めるか、範囲を絞るか、小分けにするかを参加者に確かめる。
2. **決定的なルールで置き換える**: `convert_oracle_sql_rules`で置き換えられる箇所を先に置き換える。
3. **変換する**: 下記「必ず守ること」と`workshop-custom-rules/SKILL.md`のルールに従い、次の2つを作る。
   - ソースに反映する行（置き換える行の範囲と、置き換え後の行）
   - 検査と実行に使うSQL（プレースホルダを`$1..$n`にそろえた、そのまま読めるSQL）
4. **検査する**: SQLごとに、検査用のSQLを`validate_pg_sql`で、元のSQLと検査用のSQLを`validate_bind_integrity`で
   検査する。`validate_pg_sql`の指摘は直して検査し直す（最大3回程度）。位置で指定するプレースホルダの数が
   変わった場合は、直さずに`manual_review_bind`にする。
   PostgreSQLで通るかを早く確かめたいときは、`check_postgres_sql`（変更を残さない。DMLはPREPAREで確かめる）を使ってよい。
   これは実行テストの代わりにはならない（手順5は必ず行う）。
5. **実行して確かめる**: **変換前のSQLを`run_ora_sql`で、変換後のSQLを`run_postgres_sql`で、必ず両方実行して**
   結果を比べる（SELECTは結果の行、INSERT/UPDATE/DELETEは成否と影響を受けた行数）。
   - テストケースは`tool-test-viewpoints`の観点（正常系、境界値、異常系、エッジケース）で作る。動的SQLは、分岐ごとに組み上がるSQLを作って実行する。
   - プレースホルダには、型に合ったテスト値をエージェントが決めて入れる。
   - 表がないことは、実行を省く理由にならない。
   - **DBオブジェクトのスキーマが示された場合**（例: 「DBオブジェクトはSCHEMA_SAMPLEスキーマに変換済み」）は、
     OracleとPostgreSQLの両方で、そのスキーマにある既存の表とデータで実行する。表を作らない、作り直さない。
     - Oracle: `run_ora_sql`は呼び出しごとに接続し直すため、`ALTER SESSION SET CURRENT_SCHEMA`は次の呼び出しに
       引き継がれない。実行するSQLの表名・シーケンス名にスキーマ名を付ける（例: `SCHEMA_SAMPLE.employees`）。
     - PostgreSQL: 同じ呼び出しの先頭に`SET search_path TO <スキーマ>;`を付ける（スキーマ名は小文字）。
     - スキーマ名を付けるのは、実行して確かめるためのSQLだけ。ソースに反映するSQLには付けない。
     - 既存のデータを変えない。INSERT / UPDATE / DELETEのテストは、既存の行と重ならないキーのテスト用の行を
       両方に入れ、その行に対して実行し、テストの後で削除する（シーケンスの値が進むのはよい）。
   - スキーマが示されない場合は、プロジェクトに表の定義（例: `database/schema_oracle.sql`と
     `database/schema_postgre.sql`）があればそれを、なければ必要な列だけの一時的な表を、両方のデータベースに作る。
     テストデータも入れ、テストの後で作ったものは必ず削除する。同じ名前の表やシーケンスがどちらかのデータベースに
     すでにある場合は、作らない（定義のファイルに`DROP`があっても実行しない）。既存のものを使うか、別の名前で作るかを
     ユーザーに尋ねる。
   - 結果が完全には一致しない場合は、意味が同じかを判断する。誤りなら手順3に戻る。
   - 実行がエラーになったら、エラーを見て直して試す。直しても**同じエラー（SQLSTATEとメッセージ）が2回続いたら**、
     それ以上は直さずに打ち切り、そのSQLを`fail`にして（置き換えない）、エラーと試したことを結果で伝える。
   - 結果の報告には、OracleとPostgreSQLのそれぞれで実行した内容と結果を分けて書く。実行していないことを
     「確かめた」と書かない。
6. **結果を書き出す**: `write_app_convert_outputs`で、置き換える行の範囲（元のファイルの行番号）と置き換え後の行、
   ファイルごとのテストの記録とsummary（`per_file_results`）を渡す（modeは既定の`file`。参加者の指定があればそれに従う。
   構成は`tool-output-layout`）。何回かに分けて渡してもよく、同じ出力先には前回までの
   置き換えも残る。結果の`remaining_oracle_syntax`に、変換後のファイルに残っているOracleの書き方（NVL、ROWNUMなど）が
   出たら、それも変換するか、残す理由を伝える。プレースホルダが変わる置き換えや、OracleとPostgreSQLの
   両方で実行していない状態では、ツールは書き出しを断る。データベースに接続できないなど、どうしても実行できない
   場合だけ、理由を`test_skipped_reason`に書き、ユーザーにも伝える。
7. **変換パターンを提案する**（前半の対話的な変換のときだけ）: 覚えておく価値のある変換パターンを見つけたら、
   まず結果の最後に「変換パターンの追記案」という見出しで、追記したい内容を文章で示し、`workshop-custom-rules/SKILL.md`に
   追記してよいかを尋ねる。参加者が了承したら（修正を求められたら直してから）、`write_skill_draft`で追記する。
   **了承を得る前に`write_skill_draft`を呼ばない**（このツールは、呼んだ時点でファイルに追記する）。
   追記するのは、示して了承された内容だけにする（追記のときに項目を足さない。足したい場合は、もう一度案を示す）。

## 必ず守ること

ルールが食い違うときは、1（バインド変数）を最優先にする。XMLの整形式（4）は、リテラルの中身だけを変える（2）よりも
優先する。迷ったら変換を見送る。

1. **バインド変数を変えない**
   - 位置で指定するプレースホルダ（`?`、`%s`、`$1`）は数を変えない。名前で指定するプレースホルダ（`:name`、
     `#{name}`、`${name}`）は名前と書き方を変えない（同じ名前の出現回数が変わるのはよい）。
     ホスト言語の文字列の埋め込み（`{year}`、`${expr}`、`String.format`など）も変えない。
   - `SYSDATE`などの値を新しいプレースホルダにしない（`aws_oracle_ext.sysdate()`を直接書く）。
   - `stmt.setInt(...)`などのバインドの呼び出しは変えない。
   - 例外: MyBatisの`${name}`が**値**として使われている場合（`WHERE col = ${x}`、`LIKE '%' || ${x} || '%'`など）は、
     SQLインジェクションを防ぐため`#{name}`に変えてよい。変えた箇所は結果で必ず伝える。表名・列名・`ORDER BY`の列など
     **識別子**として使われている`${name}`は、`#{name}`にすると動かなくなるため変えない。
2. **SQLの文字列リテラルの中身だけを変える**: 制御構造、変数の宣言、インデント、引用符、文字列の連結
   （`+`、`&`、`||`、`.append()`、テンプレートリテラル）の数と位置は元のままにする。SQLの長さが変わる場合も、
   今ある連結の中で配分し直す。SQL以外の行には触れない。
3. **行数はできるだけ元に近づける**: `CONNECT BY`の展開などで数行増えるのはよい。空の`""`や`.append("")`で
   埋めたり、1行に詰め込んだりしない。
4. **XMLは整形式を保つ**: SQLの中の`<`、`>`、`&`は`&lt;`、`&gt;`、`&amp;`にする（`<![CDATA[...]]>`で囲んでもよい）。
   元のファイルがすでにエンティティを使っていれば、そのまま保つ（生の文字に戻さない）。MyBatisの動的タグ
   （`<if>`、`<choose>`、`<foreach>`など）はそのまま残す。
5. **置き換える範囲の外は変えない**: importの追加や補助メソッドの追加が必要な場合は、変換を見送り、人の対応が
   必要なことを伝える。
6. **実行結果はOracleに合わせる**: 元のSQLの不具合や意図と違うと思われる動作（`ROWNUM`が並べ替えの前に採番される、
   `NVL(a || b, 'x')`の`'x'`にならないなど）も、変換では直さずにOracleと同じ結果にする。直し方は要確認として伝える。
   例外は、元のSQLがOracleでもエラーになる場合だけ（その場合も、何を直したかを伝える）。

アプリケーションがPROCEDUREを呼んでいる場合は、そのPROCEDUREがCOMMIT / ROLLBACKを含むかを確かめる。含むPROCEDUREを、
Springの`@Transactional`などトランザクションの中から`CALL`すると、PostgreSQLでは実行時にエラーになる。見つけたら、
呼び出し側の変更が必要なこととして伝える（SQLの書き換えだけでは直せない）。

これらを守ると書き換えられないSQLは、無理に変換せず、元のまま残して理由を伝える。ORMやフレームワークが方言の違いを
吸収するもの（JPQL、HQLなど）は`orm_delegated`、検証ツールの限界によるものは`validator_limitation`、それ以外は
`manual_review_range`にする。

## 後半: 残りをまとめて変換する

残りのファイルの一覧を示し、続けてよいかを確かめる。ワークショップでは、並列に変換する`scaw-migration-app-batch`を
案内する。大きいファイルは、決まった行数で区切らず、分け方を相談する。`workshop-custom-rules/SKILL.md`とこのSkillの
内容が食い違う場合は、どちらかを黙って優先せず、参加者に確認する。
